## 一、系统架构与设计

### Q1：系统采用什么架构模式？为什么这样设计？

**答**：采用**前端控制器（Front Controller）+ 分层MVC** 架构。

- **入口文件** `backend/index.php` 作为前端控制器，所有请求统一经过它进行路由分发
- **Model层**：每个数据库表对应一个Model类（如 `User.php`、`Project.php`），封装SQL操作
- **Service层**：业务逻辑层（如 `UserService.php`、`RecommendationService.php`），调用Model完成业务
- **Controller层**：每个API端点是一个 `.php` 文件（如 `api/user/login.php`），解析输入、调用Service、返回JSON

**为什么不用框架**：课程项目性质决定需要"可见的代码量"，无框架意味着所有代码都是自己写的，方便展示技术细节。

**路由实现代码** (`backend/index.php:27-48`)：
```php
$routes = [
    '/api/user/register' => 'api/user/register.php',
    '/api/user/login'    => 'api/user/login.php',
    '/api/courses'       => 'api/course/list.php',
    '/api/projects'      => 'api/project/list.php',
    // ... 10条静态路由
];
// 动态路由用正则匹配，如 /api/projects/{id}
if (preg_match('#^/api/projects/(\d+)$#', $route, $matches)) {
    $_GET['pid'] = $matches[1];
    require __DIR__ . '/api/project/detail.php';
}
```

### Q3：系统有哪些设计亮点？

1. **智能匹配推荐算法**：基于技能交集计算匹配率，Jaccard类相似度算法
2. **三层RBAC权限控制**：admin（管理员）→ leader（组长）→ member（组员）

6. **软删除模式**：user/course/project 三张表采用 `is_deleted` 标识

## 二、数据库设计

### Q5：系统有几张表？每张表的作用是什么？

**9张业务表**，全部使用 InnoDB 引擎和 utf8mb4 字符集：

| 表名 | 作用 | 核心字段 |
|------|------|----------|
| `user` | 用户账号 | uid, username, password(MD5加盐), role, credit_score, is_deleted |
| `course` | 课程信息 | cid, cname, teacher, semester, is_deleted |
| `skill` | 技能标签库 | sid, sname(唯一), category(技术/设计/管理/其他) |
| `user_skill` | 用户-技能 M:N | uid, sid(联合主键), proficiency(1-5) |
| `project` | 项目信息 | pid, cid(FK), uid(FK/组长), status(0-3), max_members, is_deleted |
| `project_skill` | 项目-需求技能 M:N | pid, sid(联合主键), required_count |
| `application` | 组队申请 | aid, pid(FK), uid(FK), status(0待处理/1接受/2拒绝/3取消) |
| `member` | 项目成员 | mid, pid, uid(联合唯一), role(leader/member) |
| `progress` | 进度节点 | prid, pid(FK), title, status(0待完成/1已完成) |

### Q6：为什么使用软删除（is_deleted）而不是物理删除？

- **数据可恢复**：误操作可以恢复
- **数据完整性**：保留历史记录，关联数据不受影响
- **审计追溯**：满足安全审计要求
- **外键约束**：物理删除会级联删除关联数据（如成员记录、申请记录），造成数据丢失

实现方式：查询时总是加 `AND is_deleted = 0` 条件。如：
```sql
SELECT * FROM user WHERE username = :username AND is_deleted = 0
```

### Q7：外键约束如何设计？为什么使用 CASCADE？

所有外键都使用 `ON DELETE CASCADE`，共11个外键约束：
```sql
CONSTRAINT `fk_p_cid` FOREIGN KEY (`cid`) REFERENCES `course`(`cid`) ON DELETE CASCADE,
CONSTRAINT `fk_p_uid` FOREIGN KEY (`uid`) REFERENCES `user`(`uid`) ON DELETE CASCADE,
-- ... 等
```

**为什么用CASCADE**：
- 保证引用完整性：删除父记录时自动清理子记录，不留孤儿数据
- 简化应用代码：不需要手动处理多表级联删除
- 配合软删除：业务中不会物理删除 user/course/project，CASCADE 是安全网而非主要机制

### Q8：为什么 member 表使用 `UNIQUE KEY (pid, uid)`？

防止用户重复加入同一项目。联合唯一约束确保一个用户在一个项目中只能有一条成员记录。这是数据库层面的防护，即使应用代码有bug也不会产生重复数据。

## 三、核心算法

### Q9：智能推荐算法是如何实现的？请详细描述。

**核心SQL** (`backend/service/RecommendationService.php:19-64`)：

**第一步：筛选候选项目**
```sql
WHERE p.status = 0            -- 只要招募中的项目
  AND p.is_deleted = 0        -- 排除软删除
  AND p.pid NOT IN (          -- 排除已加入的项目
      SELECT mm.pid FROM member mm WHERE mm.uid = :uid
  )
  AND p.pid NOT IN (          -- 排除已申请的项目
      SELECT aa.pid FROM application aa
      WHERE aa.uid = :uid AND aa.status = 0
  )
```

**第二步：计算技能匹配率**
```sql
COUNT(DISTINCT ps.sid) AS need_skills,
COUNT(DISTINCT CASE WHEN us.uid = :uid THEN us.sid END) AS matched_skills,
ROUND(
    COUNT(DISTINCT CASE WHEN us.uid = :uid THEN us.sid END) * 100.0
    / NULLIF(COUNT(DISTINCT ps.sid), 0), 2
) AS match_rate
```

**公式**：`匹配率 = (用户拥有的需求技能数 / 项目需求技能总数) × 100%`

**第三步：过滤和排序**
```sql
HAVING matched_skills > 0          -- 至少匹配1项技能
ORDER BY match_rate DESC, p.created_at DESC  -- 匹配度优先，其次最新
```

**算法特性**：
- 基于 Jaccard 相似度思想（交集/并集的变体）
- 单一SQL完成，高效
- 同时返回匹配和未匹配的技能名称，用于前端可视化展示
- 支持按课程二次筛选

### Q10：匹配算法的复杂度是多少？如果有大量用户和项目怎么办？

**当前复杂度**：
- 主查询扫描 `project × project_skill × user_skill`，复杂度 O(P×S)
- 两个NOT IN子查询各扫描member和application表

**优化方向**（如果数据量大）：
1. 添加复合索引 `(uid, sid)` 到 user_skill 表
2. 用户技能缓存（Redis），避免重复JOIN
3. 离线预计算匹配分数
4. 分页限制返回数量
5. 使用 MySQL EXPLAIN 分析执行计划

当前种子数据规模（16用户、12项目）下，查询在毫秒级完成。

### Q11：项目状态是如何自动流转的？

**状态机**（`backend/service/ApplicationService.php:86-101`）：

```
招募中(0) ──审批通过且满员──▶ 已满(1)
已满(1) ────组长手动切换───▶ 进行中(2)
进行中(2) ──组长手动结束───▶ 已结束(3)
```

**自动满员检测代码**：
```php
if ($newCount >= (int)$app['max_members']) {
    $this->projectModel->updateStatus($app['pid'], 1);   // 自动切换为"已满"
    $statusChanged = true;
}
```

事务中完成：更新申请状态 → 添加成员 → 检查满员 → 自动切换项目状态。四个操作原子执行。

### Q12：为什么推荐系统排除已申请的项目？

防止用户重复申请同一项目。如果推荐列表包含已申请的项目，用户点击后看到的可能是"您已申请过该项目，请勿重复申请"的错误提示，体验差。

另外，排除已加入的项目也是同理——用户不能同时加入同一项目两次。

## 四、安全机制

### Q13：系统采用了哪些安全措施？

**网络安全层**：
- UFW防火墙：默认拒绝入站，仅开放 22/80/443/8080
- MySQL仅监听 127.0.0.1，不暴露外网
- SSH仅密钥登录，密码登录已禁用
- fail2ban 防暴力破解

**应用安全层**：
- **SQL注入防护**：100%使用PDO预处理语句 + 参数绑定
- **密码加密**：MD5 + 用户名 + 盐值（`team_match_salt`）
- **会话安全**：`session.cookie_httponly = 1`，`session.use_strict_mode = 1`
- **路径遍历防护**：Nginx拦截 `..` 和 `~` 路径
- **信息泄露防护**：`expose_php = Off`，`display_errors = Off`，`server_tokens off`
- **文件保护**：`.git`、`.sql`、`.md`、`.log` 等敏感文件禁止外部访问
- **PHP安全**：危险函数已禁用（exec、system、passthru等），`open_basedir` 已限制

**Web安全头**：
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: SAMEORIGIN`
- `X-XSS-Protection: 1; mode=block`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: geolocation=(), microphone=(), camera=()`

### Q14：密码为什么用 MD5？有没有更好的方案？

**当前方案**：`md5(username + password + 'team_match_salt')`

**为什么用MD5**：课程项目演示性质，MD5计算简单，SQL中也支持 `MD5()` 函数（种子数据直接SQL生成）。实际生产环境应该用 bcrypt。

**改进方向**：使用 PHP 的 `password_hash()` 和 `password_verify()`：
```php
// 改进后的方案
$hash = password_hash($password, PASSWORD_BCRYPT, ['cost' => 12]);
if (password_verify($inputPassword, $storedHash)) { ... }
```
bcrypt 优势：内置盐值、计算成本可调（cost因子）、抗彩虹表、抗并行破解。

### Q15：如何防止SQL注入？

**100%使用PDO预处理语句**，所有用户输入通过参数绑定传递，绝不拼接字符串：

```php
// ✅ 正确做法
$stmt = $db->prepare("SELECT * FROM user WHERE username = :username AND is_deleted = 0");
$stmt->execute([':username' => $username]);

// ❌ 绝不这样做
$stmt = $db->query("SELECT * FROM user WHERE username = '$username'");
```

关键配置：`PDO::ATTR_EMULATE_PREPARES => false`，强制使用MySQL原生预处理，而非PHP模拟。

### Q16：为什么登录失败提示"用户名或密码错误"而不是分开提示？

**安全考虑**：防止用户名枚举攻击。如果分别提示"用户名不存在"和"密码错误"，攻击者可以通过尝试不同用户名来发现系统中存在的账号。

统一错误信息让攻击者无法判断是用户名不对还是密码不对。

## 五、认证与权限

### Q17：认证机制是如何工作的？为什么不使用JWT？

**当前方案**：PHP Session（服务端会话）

```php
// 登录时设置session
$_SESSION['uid'] = $user['uid'];
$_SESSION['username'] = $user['username'];
$_SESSION['role'] = $user['role'] ?? 'member';

// 鉴权时检查session
if (!isset($_SESSION['uid'])) {
    Response::unauthorized('请先登录');
    exit;
}
```

**为什么用Session而非JWT**：
1. 系统是单体PHP应用，无微服务拆分需求
2. Session存储在服务端，可以随时撤销（踢人下线）
3. 不需要在客户端维护Token刷新逻辑
4. 避免JWT的无状态注销难题
5. 课程项目，适合从传统Session入手学习

### Q18：前端的Token机制和后端的Session机制如何兼容？

前端 `api.js` 统一使用 `credentials: 'include'` 发送请求，自动携带浏览器Cookie。同时兼容两种模式：

**Python模式**（开发环境）：
```javascript
if (authToken) {
    opts.headers = { 'Authorization': 'Bearer ' + authToken };
}
```

**PHP模式**（生产环境）：
- Session Cookie自动随请求发送
- Authorization头被PHP忽略（PHP用Session），但不影响请求

两种模式共用同一套前端代码，无需修改 `api.js`。

### Q19：如何实现"组长才能审批"这个权限校验？

**多层校验** (`backend/middleware/Auth.php:42-48`)：

```php
public static function isProjectLeader($pid, $uid)
{
    $db = Database::getInstance();
    $stmt = $db->prepare("SELECT uid FROM project WHERE pid = :pid AND is_deleted = 0");
    $stmt->execute([':pid' => $pid]);
    $project = $stmt->fetch();
    return $project && (int)$project['uid'] === (int)$uid;
}
```

1. 先通过 `requireLogin()` 确认已登录
2. 查询数据库验证被操作项目的 `uid` 是否等于当前用户
3. 不是组长则返回403

### Q21：前端如何实现请求失败自动重试？

**api.js 中的重试机制** (`frontend/js/api.js:31-60`)：

```javascript
async function request(method, path, body, params, retryCount) {
    retryCount = retryCount || 0;
    // ...构建请求...

    try {
        var res = await fetchWithTimeout(url, opts, 10000);  // 10秒超时
        var data = await res.json();
        handleResponse(data);
        return data;
    } catch (err) {
        if (retryCount < 1) {         // 最多重试1次
            await new Promise(function(r) { setTimeout(r, 800); });  // 等待800ms
            return request(method, path, body, params, retryCount + 1);
        }
        throw err;  // 重试后仍失败，抛出异常
    }
}
```

关键参数：**10秒超时 + 800ms重试间隔 + 最多1次重试**。这是科学的选择：
- 10秒超时：足够慢网络完成请求，但不会让用户等太久
- 800ms间隔：给服务器短暂恢复时间
- 只重试1次：防止雪崩效应

## 七、部署运维

### Q23：系统是如何部署到服务器的？

**服务器环境**：Ubuntu 22.04.5 LTS，Nginx + PHP-FPM 8.4，MySQL 8.0

**部署路径**：`/opt/teammatch/`
- `backend/` — PHP后端代码
- `frontend/` — 前端静态文件
- `backend/sql/` — 数据库脚本

**Nginx关键配置**：直接代理 API 到 PHP 入口文件
```nginx
location /api/ {
    include fastcgi_params;
    fastcgi_pass unix:/run/php/php8.4-fpm.sock;
    fastcgi_param SCRIPT_FILENAME /opt/teammatch/backend/index.php;
    fastcgi_param SCRIPT_NAME /index.php;    # ★ 关键：前端控制器路径
}
```

`SCRIPT_NAME /index.php` 是整个路由系统正常工作的关键——PHP的 `dirname()` 基于它计算basePath。

### Q24：Nginx路由404问题是怎么解决的？

**问题现象**：API返回404，PHP报 "Primary script unknown"

**根因**：`SCRIPT_NAME` 配置为 `/backend/index.php`，导致 PHP 路由计算错误：
```php
$scriptName = dirname($_SERVER['SCRIPT_NAME']);  // dirname('/backend/index.php') = '/backend'
$basePath = '/backend';
$route = substr('/api/courses', 8);  // 从第8位截取，得到错误路由
```

**解决方案**：将 `SCRIPT_NAME` 改为 `/index.php`：
```php
$scriptName = dirname('/index.php');    // = '/'
$basePath = '';
$route = substr('/api/courses', 0);     // = '/api/courses' ✓
```

## 八、代码质量与工程实践

### Q26：项目中使用了哪些设计模式？

1. **单例模式**：`Database` 类（`util/Database.php`）
   ```php
   private static $instance = null;
   public static function getInstance() { ... }
   ```

2. **前端控制器模式**：`index.php` 统一处理所有请求路由

3. **自动加载模式**（PSR-4风格）：`spl_autoload_register` 按目录搜索类文件
   ```php
   spl_autoload_register(function ($class) {
       $paths = ['util/', 'middleware/', 'service/', 'model/'];
       foreach ($paths as $path) {
           $file = __DIR__ . '/' . $path . $class . '.php';
           if (file_exists($file)) { require_once $file; return; }
       }
   });
   ```

4. **静态工厂方法**：`Response` 类提供语义化静态方法
   ```php
   Response::success($data, '操作成功');
   Response::unauthorized('请先登录');
   Response::forbidden('权限不足');
   Response::notFound('资源不存在');
   ```

5. **服务层模式**：业务逻辑在Service类中，API文件只做输入输出

### Q27：如何保证API返回格式的一致性？

所有API通过 `Response` 类返回统一JSON格式：

```json
{
    "code": 200,
    "message": "操作成功",
    "data": { ... }
}
```

**语义化的HTTP状态码映射**：
```php
Response::success()      → code:200
Response::badRequest()   → code:400
Response::unauthorized() → code:401
Response::forbidden()    → code:403
Response::notFound()     → code:404
Response::serverError()  → code:500
```

### Q28：事务在哪些地方使用？为什么？

**两处使用数据库事务**：

**1. 项目发布** (`ProjectService::create`)：
```php
$db->beginTransaction();
try {
    $pid = $this->projectModel->create(...);           // 创建项目
    foreach ($data['skill_ids'] as $sid) {
        $this->projectModel->addRequiredSkill($pid, $sid);  // 添加需求技能
    }
    $this->projectModel->addMember($pid, $uid, 'leader');   // 添加创建者为组长
    $db->commit();
} catch (Exception $e) {
    $db->rollBack();
}
```

**2. 审批申请** (`ApplicationService::handleApplication`)：
```php
$db->beginTransaction();
try {
    $this->applicationModel->updateStatus($aid, 1);      // 更新申请状态
    $this->projectModel->addMember($pid, $uid, 'member'); // 添加成员
    if (满员) $this->projectModel->updateStatus($pid, 1); // 自动切换状态
    $db->commit();
} catch (Exception $e) {
    $db->rollBack();
}
```

**为什么用事务**：这些操作涉及多表写入，必须原子执行——要么全部成功，要么全部回滚。防止出现"项目创建了但技能没关联"或"申请通过了但成员没加入"的数据不一致。

### Q29：批量查询优化是如何实现的？

**问题**：N+1查询。获取项目列表后，为每个项目单独查询技能名称。

**优化方案**：在管理后台的项目列表中，使用 `WHERE pid IN (...)` 一次查询所有项目的技能：

```php
// 先收集所有项目ID
$pids = array_column($projects, 'pid');
// 批量查询
$stmt = $db->prepare(
    "SELECT ps.pid, s.sname FROM project_skill ps
     JOIN skill s ON ps.sid = s.sid
     WHERE ps.pid IN (" . implode(',', array_fill(0, count($pids), '?')) . ")"
);
$stmt->execute($pids);
// 分组到各项目
foreach ($skillRows as $row) {
    $skillMap[$row['pid']][] = $row['sname'];
}
```

**效果**：12个项目从13次查询变为2次查询（减少85%），大规模场景收益更大。

### Q30：为什么选择PDO的 `EMULATE_PREPARES = false`？

```php
$options = [
    PDO::ATTR_EMULATE_PREPARES => false,  // 使用MySQL原生预处理
];
```

**原因**：
1. **真正的SQL注入防护**：原生预处理在MySQL服务端编译SQL，参数值不可能改变SQL结构
2. **类型安全**：原生预处理保持数据类型（INT就是INT，不会变成字符串）
3. **性能**：原生预处理语句可以在MySQL端重复使用执行计划
4. PHP模拟的预处理（默认行为）本质是客户端转义后拼接，不如原生安全

## 九、双模式兼容（Python vs PHP）

### Q31：为什么有两套后端（Python和PHP）？

| 环境 | 后端 | 数据库 | 用途 |
|------|------|--------|------|
| 本地开发 | `server.py` (Python) | SQLite | 快速开发调试，无需安装Nginx+PHP+MySQL |
| 生产部署 | PHP `index.php` + 多文件 | MySQL | 正式运行，Nginx+PHP-FPM |

**本地用Python的原因**：`python server.py` 一键启动，不需要配置Web服务器和数据库环境。

**生产用PHP的原因**：与Nginx天然适配，PHP-FPM进程管理成熟，MySQL支持事务和外键。

### Q32：两套后端的API接口完全兼容吗？

**是的，前端代码无需任何修改。** 关键实现：

1. **统一的JSON响应格式**：两套后端都返回 `{"code":int, "message":string, "data":mixed}`
2. **前端认证自适应**：
   ```javascript
   // Python模式：手动设置Authorization头
   if (authToken) opts.headers = {'Authorization': 'Bearer ' + authToken};
   // PHP模式：credentials: 'include' 自动携带Session Cookie
   opts.credentials = 'include';
   ```
3. **API路径完全一致**：两套后端的URL路径命名相同
4. **Python模式前端同时处理API和静态文件**：设计为同端口下前端也由Python服务

差异仅在底层实现（Token vs Session、SQLite vs MySQL），接口层完全透明。

### Q36：这个项目中你遇到的最大技术挑战是什么？

**API路由404问题**。Nginx配置中 `SCRIPT_NAME` 的路径直接影响了PHP路由计算，但错误信息不明显。

排查过程：
1. 首先通过 `curl -v` 看HTTP状态码
2. 在PHP中添加 `var_dump` 调试输出看路由变量
3. 发现 `dirname('/backend/index.php')` 返回 `/backend`
4. 而请求路径是 `/api/courses`
5. `substr('/api/courses', 8)` 截取结果错误
6. 最终将 `SCRIPT_NAME` 改为 `/index.php` 解决

经验：中间件配置的细节往往是最难排查的，因为错误出现在框架层面而非业务代码。

### Q37：你是如何保证代码安全的？

1. **SQL注入**：100% PDO预处理语句，零字符串拼接SQL
2. **XSS**：前端使用 `textContent` 而非 `innerHTML`，避免HTML注入
3. **CSRF**：SameSite Cookie + Session机制
4. **路径遍历**：Nginx拦截 `..` 路径，PHP `open_basedir` 限制文件访问
5. **信息泄露**：隐藏PHP版本、Nginx版本、数据库错误详情
6. **暴力破解**：fail2ban防护 + 统一错误提示防止用户名枚举

### Q38：如果用户量增长到1万，推荐算法需要多长时间？

当前算法单次查询复杂度约为 O(项目数 × 平均需求技能数)。假设1万用户、1000个招募中项目、每项目4个技能：

- MySQL JOIN扫描：1000 × 4 = 4000 行（project_skill）
- 子查询排除：1000行扫描（member）+ 1000行扫描（application）
- 预计时间：**50-200ms**（有索引的情况下）

瓶颈不在计算而在数据库JOIN。如果进一步优化：
- 使用Redis缓存用户技能向量
- 离线预计算匹配分数，每分钟刷新
- 可以使用Elasticsearch的向量搜索

### Q39：项目中的信用分（credit_score）字段有什么用途？

信用分是用户行为评价机制的基础设计：
- 默认值：100
- 设计意图：用户迟到/违约扣分，按时完成加分
- 当前状态：字段已定义，seed data中有差异化数值（70-100），但评分逻辑尚未实现

这是预留的扩展点，用于后续迭代中的"用户信用体系"功能。

### Q40：软删除的数据如何真正删除？

如果需要物理删除，步骤是：
1. 先删除关联子表数据（member、application、progress）
2. 再删除项目表记录
3. 或利用CASCADE外键自动级联删除

但在业务层面，系统设计为永不物理删除——这符合数据审计和追溯的最佳实践。
